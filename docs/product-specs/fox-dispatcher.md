# Продуктовая спецификация: «Лисий диспетчер»

Статус: утверждённый контракт для реализации

Сценарий: вариант 01 тестового задания MOX AI-first Developer

План реализации: [2026-07-16-fox-dispatcher-implementation.md](../exec-plans/active/2026-07-16-fox-dispatcher-implementation.md)

## Цель продукта

«Лисий диспетчер» помогает лесному смотрителю работать с набором наблюдений: понять, сколько лис замечено, где сосредоточена активность, какая лиса лидирует по объяснимому индексу подозрительности и из каких исходных признаков сложился результат.

Интерфейс демонстрирует изменение результата двумя путями:

- изменение самих наблюдений;
- изменение явной политики оценки — влияния признака добычи.

Результат представляет собой связанную систему: главный вывод, рейтинг, активность по локациям, доказательства, исходные записи и пояснение формулы.

## Пользователь и основной сценарий

Основной пользователь — лесной смотритель, которому нужно быстро оценить текущую выборку наблюдений и проверить основания вывода.

Целевой сценарий проверки:

1. Открыть приложение и без настройки увидеть стартовые данные.
2. Считать 5 наблюдений, 4 уникальные лисы и главную локацию.
3. Увидеть лидера `fox_001` с индексом 7,8.
4. Открыть расчёт и исходные наблюдения этой лисы.
5. Изменить влияние добычи с 20% на 30%.
6. Увидеть новым лидером `fox_003` с индексом 7,9.
7. Изменить наблюдение и увидеть синхронный пересчёт всех частей отчёта.
8. Открыть AI Worklog и проверить процесс разработки по артефактам.

## Поля и их семантика

| Поле | Значение в продукте | Вклад в индекс |
|---|---|---:|
| `id` | Уникальный технический идентификатор наблюдения | Нет |
| `fox_id` | Идентификатор, объединяющий наблюдения одной лисы | Только группировка |
| `location` | Зафиксированное название места наблюдения | Нет |
| `color` | Цвет, зафиксированный в конкретном наблюдении | Нет |
| `has_prey` | Наблюдаемый факт наличия добычи | Да |
| `suspicion_level` | Прямая оценка подозрительности, выставленная смотрителем | Да |
| `time` | Время записи внутри текущей выборки | Нет |

`location`, `color` и `time` дают контекст, фильтрацию и хронологию. Количество записей одной лисы показывает объём доказательств. Эти значения не получают скрытых коэффициентов.

Цвет принадлежит наблюдению. Если записи одной лисы содержат разные цвета, сводка показывает последний зафиксированный цвет и отмечает наличие нескольких значений в подробностях.

## Значение «текущей выборки»

Данные содержат время, но не дату. Продукт называет расчёт `текущей выборкой` или `текущим набором наблюдений`.

Время используется для:

- сортировки записей;
- определения последнего наблюдения;
- разрешения равенства в рейтинге.

Время не означает давность в днях и не создаёт recency-бонус. Формулировки про буквальное «сегодня», live-состояние или вероятность будущего поведения не входят в продуктовый контракт.

## Объяснимая модель оценки

### Назначение индекса

Индекс подозрительности — число от 0 до 10 для относительного приоритета внимания внутри активной выборки. Это не вероятность опасности и не автоматическое обвинение.

### Агрегаты лисы

Для каждой лисы `f`:

```text
meanSuspicion(f) = среднее suspicion_level всех записей f
preyRate(f)      = записи f с has_prey=true / все записи f
preySignal(f)    = preyRate(f) × 10
```

### Формула

```text
score(f) =
  meanSuspicion(f) × (1 − preyWeight)
  + preySignal(f) × preyWeight
```

Начальное значение `preyWeight = 0.20`. Пользователь меняет его от 0 до 1 с шагом 0.05. Вес прямой оценки автоматически равен `1 − preyWeight`.

Текст рядом с настройкой объясняет допущение: добыча считается настраиваемым сигналом диспетчерского внимания. При весе 0% рейтинг буквально следует только `suspicion_level`.

### Сортировка и округление

Рейтинг сортируется по:

1. неокруглённому `score`, по убыванию;
2. `meanSuspicion`, по убыванию;
3. времени последнего наблюдения, от позднего к раннему;
4. `fox_id`, лексикографически по возрастанию.

Интерфейс показывает один знак после запятой. Порядок определяется исходным неокруглённым значением, поэтому вычисление остаётся стабильным.

### Стартовый результат 80/20

| Лиса | Средняя оценка | Доля добычи | Вклад оценки | Вклад добычи | Итог |
|---|---:|---:|---:|---:|---:|
| `fox_001` | 8,5 | 50% | 6,8 | 1,0 | **7,8** |
| `fox_003` | 7,0 | 100% | 5,6 | 2,0 | **7,6** |
| `fox_002` | 5,0 | 0% | 4,0 | 0,0 | **4,0** |
| `fox_004` | 3,0 | 0% | 2,4 | 0,0 | **2,4** |

### Демонстрационный пересчёт 70/30

При `preyWeight = 0.30`:

```text
fox_003 = 7.0 × 0.70 + 10 × 0.30 = 7.90
fox_001 = 8.5 × 0.70 + 5 × 0.30  = 7.45
```

Лидером становится `fox_003`; в интерфейсе его значение отображается как 7,9.

## Состав отчёта

### Сводные показатели

Стартовая выборка даёт:

- 5 наблюдений;
- 4 уникальные лисы;
- 3 локации;
- Северная поляна — 3 из 5 наблюдений, 60%;
- последнее наблюдение — `fox_004`, 12:10;
- лидер рейтинга — `fox_001`, 7,8 при политике 80/20.

### Рейтинг

Для каждой лисы отчёт предоставляет:

- позицию;
- `fox_id`;
- итоговый индекс;
- среднюю прямую оценку;
- количество записей с добычей и общее количество;
- время и место последней записи;
- последний зафиксированный цвет;
- объём доказательств.

### Объяснение выбранной лисы

Подробность содержит:

- итоговый балл;
- оба точных вклада;
- текущую политику весов;
- исходные наблюдения в обратном хронологическом порядке;
- количество наблюдений как контекст;
- явный перечень полей, которые в индекс не входят.

### Активность по локациям

Активность означает количество наблюдений. Для каждой локации показываются абсолютное число и доля активной выборки. Этот показатель не смешивается с подозрительностью.

## Область фильтрации

Глобальные фильтры:

- поиск по `fox_id`;
- локация;
- цвет;
- добыча: все / есть / нет.

Фильтры определяют всю область отчёта: сводные числа, рейтинг, активность по локациям, выбранные доказательства и список наблюдений рассчитываются из одного набора.

Интерфейс постоянно показывает `Отчёт по N из M наблюдений`. Активные фильтры представлены удаляемыми элементами, а общий сброс возвращает полный набор.

Клик по локации в сводке применяет соответствующий фильтр и обновляет область отчёта.

## Управление наблюдениями

### Добавление

Пользователь вводит `fox_id`, `location`, `color`, `has_prey`, `suspicion_level` и `time`. `id` создаётся приложением и отображается как техническое значение.

Принятое наблюдение немедленно обновляет отчёт и сохраняется локально.

### Редактирование

Редактор показывает поля записи один к одному. `id` сохраняется неизменным. Сохранение применяется атомарно; отмена оставляет состояние прежним. Выход из изменённой формы предлагает сохранить или отказаться от изменений.

### Удаление

Удаление сопровождается кратковременной отменой. Удаление единственной записи лисы уменьшает число уникальных лис. Удаление последней записи всего набора переводит приложение в пустое состояние.

## JSON import и export

### Import

Основной import полностью заменяет набор после явного подтверждения:

```text
выбрать файл или вставить JSON
-> распарсить
-> проверить
-> показать preview
-> подтвердить замену
```

Preview показывает:

- количество записей;
- число уникальных лис;
- локации;
- диапазон времени;
- ошибки с адресом поля;
- предупреждение о замене текущего набора.

Одна ошибка делает применение недоступным. Текущее состояние и введённый JSON сохраняются для исправления.

### Boundary validation

- корень — массив не более 1000 записей;
- `id` — уникальная непустая строка до 64 символов;
- `fox_id` — непустая строка до 64 символов;
- `location` и `color` — непустые строки до 80 символов;
- строки очищаются от окружающих пробелов;
- `has_prey` — строгий boolean;
- `suspicion_level` — конечное целое число от 0 до 10;
- `time` — реальное 24-часовое время `HH:mm`;
- повторяющийся `fox_id` допустим;
- пустой массив допустим после подтверждения;
- неизвестные поля считаются ошибкой контракта, чтобы import не терял данные молча.

Пользовательский текст выводится как текстовое содержимое. HTML-разметка из импортированных значений не интерпретируется.

### Export

Export создаёт JSON полного набора наблюдений в формате import. Активные фильтры не сокращают экспортируемые данные.

## Локальное сохранение

Состояние браузера содержит:

```text
schemaVersion
observations
scoringPolicy.preyWeight
updatedAt
```

После перезагрузки восстанавливаются наблюдения и политика оценки. Фильтры начинают новую сессию сброшенными, чтобы сохранённая ограниченная выборка не скрывала данные при возвращении.

Повреждённое сохранение даёт выбор между стартовыми данными и просмотром/копированием доступного сырого значения. При недоступном storage продукт продолжает работать в памяти и сообщает, что изменения сохранятся только до закрытия страницы.

Сброс данных и сброс веса модели — разные действия. Сброс данных возвращает исходные пять записей после подтверждения; сброс веса возвращает 20% рядом с контролом.

## Состояния интерфейса

| Состояние | Результат и следующий шаг |
|---|---|
| Первый запуск | Стартовые 5 записей и полный рассчитанный отчёт |
| Пустой набор | Лидер отсутствует; доступны добавление, import и восстановление стартовых данных |
| Фильтры дали 0 | Исходные данные сохранены; видны область 0 из M и сброс фильтров |
| Ошибка формы | Краткое резюме и ошибки у полей; введённые значения сохраняются |
| Ошибка import | Путь и причина ошибки; текущее состояние не меняется |
| Повреждённый storage | Понятное восстановление и доступ к сырому значению |
| Storage недоступен | Работа в памяти с явным статусом несохраняемого состояния |
| Равные индексы | Детерминированный порядок по зафиксированным tie-breaks |

Нулевой набор не создаёт фиктивного лидера с нулевым баллом.

## AI Worklog

AI Worklog доступен из основной навигации и содержит 5-7 фактических чекпоинтов. Публичная запись чекпоинта включает:

- вопрос или цель;
- вклад AI;
- решение человека;
- изменение продукта или репозитория;
- доказательство проверки.

Worklog хранит краткий результат процесса вместо полной переписки. Секреты, токены, приватные абсолютные пути, клиентские данные и личная информация исключаются из публичного источника.

## Нефункциональные требования

- Статическое React-приложение развёртывается на Vercel.
- Пользовательские наблюдения остаются в браузере.
- Производственный runtime не требует backend или AI API.
- Основной сценарий работает клавиатурой.
- Интерфейс сохраняет функциональность при ширине 320 CSS px и увеличении 200%.
- Результат, состояние и ошибки доступны не только через цвет.
- Production build не содержит секретов, приватных путей и debug-артефактов.

Подробный accessibility и responsive контракт находится в [interface.md](../design-docs/interface.md).

## Приёмочные сценарии

1. Старт показывает 5 наблюдений, 4 лисы и Северную поляну 3/5.
2. При 20% добычи `fox_001` получает 7,8 и занимает первое место.
3. При 30% добычи `fox_003` получает 7,9 и занимает первое место.
4. Изменение `obs_005.suspicion_level` на 10 даёт `fox_004` 8,0 при политике 80/20.
5. Фильтр `Северная поляна` даёт 3 наблюдения и 2 лисы во всём отчёте.
6. Удаление единственной записи `fox_004` уменьшает число уникальных лис с 4 до 3.
7. Некорректный import сообщает адрес поля и не меняет текущий набор.
8. Корректный import применяется только после preview и подтверждения.
9. Перезагрузка восстанавливает данные и политику оценки.
10. Сброс возвращает исходные пять наблюдений, а отдельный сброс модели — вес 20%.
11. AI Worklog показывает 5-7 реальных public-safe checkpoints.
12. Публичный Vercel URL воспроизводит основной сценарий на desktop и mobile без console errors.

## Границы версии

Первая версия фокусируется на одном пользователе и одном локальном наборе наблюдений. Карта, координаты, синхронизация между устройствами, роли, аккаунты, серверная база, patrol workflow, runtime AI, прогнозы и вероятностная уверенность не входят в эту поставку.

Эти границы сохраняют проверяемость тестового задания: редактируемые вводные, прозрачная логика, живой результат, качественный интерфейс и видимый AI-first процесс.
